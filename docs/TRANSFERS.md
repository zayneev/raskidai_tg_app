## Поведение и переходы

Расчёт, суммы, отправители и получатели берутся только из неизменяемого snapshot
этапа 5 и не пересчитываются при отметках. Деньги остаются целыми
`bigint`-копейками. Приложение не создаёт банковский платёж и не проверяет
реальное движение денег — оно хранит только отметки участников.

| Текущее состояние | Кто действует | Действие                  | Новое состояние |
| ----------------- | ------------- | ------------------------- | --------------- |
| `pending`         | отправитель   | отметить отправленным     | `sent`          |
| `sent`            | получатель    | подтвердить получение     | `confirmed`     |
| `sent`            | получатель    | сообщить «Не получил»      | `not_received`  |
| `not_received`    | отправитель   | повторно отметить отправку | `sent`          |

Повтор уже достигнутого действия идемпотентен и не добавляет историю. После
`confirmed` перевод неизменяем. Получение и проблема недоступны в `pending`.
Чужой, неактивный или относящийся к другому settlement перевод недоступен.
`sentAt`, `confirmedAt`, `notReceivedAt` и время истории назначает сервер.

Первая фактическая отметка `sent` навсегда заполняет
`settlements.transfers_started_at`. Поэтому возврат settlement в `draft`
разрешён создателю только до начала переводов и запрещён после `not_received`.
Проверка marker, истории и текущего состояния атомарна под той же блокировкой
`events`, что и отправка. Завершённое мероприятие вернуть в `draft` нельзя.

Последнее подтверждение атомарно меняет событие `settled → completed`. Пока
существует `pending`, `sent` или `not_received`, завершения нет. Расчёт без
переводов сразу создаётся как `completed`; миграция также завершает ранее
созданные активные нулевые расчёты с увеличением версии события.

## HTTP/RPC-контракт

`POST /functions/v1/events`, `Authorization: Bearer <app session token>`, JSON.

| action                   | Разрешённые поля                                      |
| ------------------------ | ----------------------------------------------------- |
| `transfers.send`         | `eventId`, `transferId`, `eventVersion`, `requestId` |
| `transfers.confirm`      | `eventId`, `transferId`, `eventVersion`, `requestId` |
| `transfers.not_received` | `eventId`, `transferId`, `eventVersion`, `requestId` |

Успех возвращает `{ ok, eventVersion, eventStatus, transfer }`; `transfer`
содержит серверные `id`, `status`, `sentAt`, `confirmedAt`, `notReceivedAt`.
Полный актуальный расчёт участники получают прежним `settlements.get`.

HTTP-слой передаёт только allowlist выше. `userId`, `status`, сумма, стороны,
времена и готовый результат игнорируются. RPC определяет пользователя по SHA-256
токена app-сессии. Порядок блокировок: `app_sessions FOR SHARE → events FOR
UPDATE → active settlements FOR UPDATE → transfers FOR UPDATE`. Срок/отзыв
сессии повторно проверяется после ожидания каждой прикладной блокировки.

`transfer_requests` хранит точный action/body без самого `requestId` и точный
успешный ответ в одной транзакции. Тот же ID и тело возвращают исходный ответ;
другое тело даёт `request_conflict`. Каждый фактический переход создаёт одну
неизменяемую строку `transfer_status_history` с actor, action, before/after и
серверным временем. Повтор не создаёт историю и не увеличивает версию.

Ошибки: 400 `invalid_input`/`invalid_action`; 401 `unauthorized`; 403
`forbidden`; 404 `not_found`; 409 `version_conflict`, `request_conflict`,
`invalid_transition`, `transfer_unavailable`, `event_locked`,
`transfers_started`.

## Интерфейс

Отправитель видит «Отметить отправленным» только для своего `pending` или
`not_received`; получатель после `sent` видит «Получил» и «Не получил». Каждое
действие требует подтверждения. До ответа сервера статус не меняется. При
неоднозначной сетевой ошибке в памяти остаются точные body/requestId для повтора;
определённая 4xx-ошибка очищает pending request и предлагает обновить данные.

Карточка показывает статус и известные времена. Для `not_received` отправителю
показана просьба проверить реквизиты и повторить реальную отправку вне приложения.
После всех подтверждений видно завершение; при пустом списке — завершение без
переводов. Действия без прав не рендерятся.

## Безопасность и ограничения

Новые таблицы имеют RLS без разрешающих политик. У `anon`/`authenticated` нет
табличных прав и EXECUTE на RPC; `service_role` может только читать/добавлять
request/history, но не изменять и не удалять их. RPC — `SECURITY INVOKER`, ключ
остаётся только в Edge Function. FK связывают историю с тем же
event/settlement/transfer; новые FK индексированы.

RLS INFO намеренно соответствует закрытой модели и не означает публичный доступ:
[описание проверки](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

Frontend не выполняет realtime/polling: другой участник нажимает «Обновить».
Pending request хранится в памяти и исчезает после перезагрузки; серверная
идемпотентность сохраняется. История переходов хранится в БД, отдельного экрана
полной истории в MVP нет. Списки без пагинации при лимите 30 участников.

## Реальная приёмка в Telegram

1. A создаёт мероприятие с B и C и минимум двумя переводами; A фиксирует расчёт.
2. Только отправитель видит свою кнопку отправки. Получатель и C отправить его
   перевод не могут.
3. Отправитель подтверждает предупреждение и отмечает `sent`. Получатель после
   обновления видит «Получил»/«Не получил»; остальные этих кнопок не видят.
4. Получатель выбирает «Не получил». Событие не завершается, отправитель видит
   предупреждение и повторяет отправку. Проверить показанные времена.
5. Получатель подтверждает перевод. У `confirmed` действий больше нет; пока
   второй перевод не подтверждён, событие остаётся `settled`.
6. Последнее подтверждение: все аккаунты после обновления видят «Завершено»;
   расходы, участники, приглашения и расчёт остаются заблокированы.
7. До отправки в отдельном событии создатель возвращает расчёт в `draft`;
   повтор не дублирует историю. После `sent`, включая последующий
   `not_received`, возврат запрещён.
8. Оборвать сеть при отметке и нажать безопасный повтор: переход и история
   возникают один раз. При конфликте версии обновить карточку.
9. Зафиксировать событие без переводов: оно сразу завершено без ручных отметок.
