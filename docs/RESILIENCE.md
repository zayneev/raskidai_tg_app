# Этап 7: устойчивость, восстановление и история

Этап 7 реализован 14.09.2026 в существующем проекте Supabase
`njzfzgqprgkyrqirkvhe`. Миграция `20260914103425_resilience_history` применена,
Edge Function `events` опубликована как версия 6. Frontend проверен локально;
публикация GitHub Pages не запускалась.

## Архитектура запросов

Frontend использует один модуль запросов с четырьмя раздельными состояниями:

- первоначальная загрузка без данных;
- фоновое обновление с сохранением уже показанных данных;
- изменяющий запрос с блокировкой повторного tap;
- явный повтор сохранённого неоднозначного запроса.

Каждый запрос получает отдельный `AbortController`. Запрос отменяется при
размонтировании, смене мероприятия или пользователя. Таймаут frontend — 15 секунд,
вызов PostgreSQL из Edge Function ограничен 10 секундами. Одинаковые чтения без
component signal дедуплицируются; внутри экранов предыдущая загрузка отменяется до
новой. Изменяющие запросы автоматически не повторяются.

Безопасные чтения повторяются не более двух раз после обрыва, timeout или 5xx с
backoff 250/750 мс. `offline` не запускает сетевой запрос. Бесконечных циклов нет.

## Классификация ошибок

| Состояние                           | Поведение                                                         |
| ----------------------------------- | ----------------------------------------------------------------- |
| offline                             | сохраняются данные и форма, показывается жёлтый индикатор         |
| timeout / обрыв                     | результат мутации неизвестен; сохраняется точное тело             |
| cancelled                           | сообщение не показывается, блокировка интерфейса снимается        |
| 401                                 | начинается контролируемый повторный Telegram-вход                 |
| 403                                 | действие недоступно; локальная форма при потере прав очищается    |
| 404                                 | объект или членство недоступны; локальная форма объекта очищается |
| 409                                 | показывается конкретный код конфликта и предлагается обновление   |
| 5xx                                 | чтение ограниченно повторяется; мутация остаётся pending          |
| не-JSON / некорректная форма ответа | отдельная безопасная ошибка без деталей БД                        |

`request_conflict`, `version_conflict`, `invalid_transition`, `event_locked`,
`transfer_unavailable`, `transfers_started`, `forbidden`, `not_found` и
`unauthorized` имеют отдельные русские сообщения. SQL-текст, stack trace, ключи,
токены и детали инфраструктуры пользователю не возвращаются.

## requestId и неоднозначный результат

Новый frontend отправляет UUID `requestId` с каждой мутацией: создание и вход в
мероприятие, приглашение, выход, расходы, фиксация/отмена и переходы переводов.
Перед отправкой точные `action`, тело и `requestId` сохраняются локально. Повтор
после timeout, обрыва, неизвестного 5xx или повторного входа отправляет тот же
объект без изменений. Автоматического повтора мутаций и оптимистического успеха
нет. Изменение формы удаляет старый pending и следующая отправка получает новый
UUID.

`event_requests` дополняет существующие `expense_requests`,
`settlement_requests` и `transfer_requests`. Таблица хранит точные внутренние
payload/response, закрыта от `anon`/`authenticated`, имеет RLS без разрешающих
политик и доступна `service_role` только для `SELECT/INSERT`. Повтор проверяет
действующую app-сессию после ожидания блокировки события. Другое тело с тем же
requestId возвращает `request_conflict`.

Старый HTTP/frontend этапов 3–6 во время развёртывания остаётся совместим:
HTTP-обработчик и внутренний RPC принимают прежние event-мутации без requestId,
но новый frontend всегда отправляет requestId. Ранее созданные мероприятия
перенесены в журнал с legacy-marker и сохраняют прежний результат повтора.

Токен приглашения для `rotate` детерминированно выводится на сервере HMAC-SHA-256
из server-only service key, eventId и requestId. Поэтому тот же запрос получает ту
же ссылку, а в БД по-прежнему хранится только SHA-256 capability. Service key и
исходный app-session token во frontend не передаются.

## Локальное хранилище

Формат envelope:

```text
{
  version: 1,
  userId,
  eventId,
  operation,
  kind: "draft" | "pending",
  updatedAt,
  expiresAt,
  data
}
```

Namespace:
`raskidai:v1:<internal-user>:<event|global>:<operation>:<draft|pending>`.
Черновики живут 7 суток, pending requests — 24 часа. Восстановленные записи
проверяются по версии, scope, сроку, разрешённой операции и ожидаемым типам.
Повреждённые и просроченные записи удаляются. Pending никогда не отправляется
автоматически: пользователь выбирает точный повтор или отказ.

В localStorage нет Telegram initData, app-session token, Authorization header,
service role, Bot Token или иных серверных секретов. При выходе записи текущего
внутреннего userId удаляются; в любом случае namespace не позволяет следующему
аккаунту их увидеть. Локальные данные никогда не считаются серверной истиной.

Черновик очищается после подтверждённого успеха, явной отмены, недоступности
объекта, потери прав или блокировки мероприятия. Фоновое обновление не закрывает
форму. Если event version изменилась во время редактирования расхода, интерфейс
показывает предупреждение до отправки.

## Сессия и восстановление сети

HTTP 401 очищает только session token в памяти и запускает повторный обмен свежего
Telegram initData. Форма и pending остаются в локальном scope. После успешного
входа данные читаются заново, но мутация автоматически не повторяется. Если
initData уже старше пяти минут, пользователь получает просьбу закрыть Mini App и
открыть его снова.

События `online`, `offline` и `visibilitychange` отслеживаются. При возвращении
видимой вкладки или сети открытая карточка безопасно перечитывается. Ручная кнопка
«Обновить» сохранена. Постоянный polling и Realtime не используются: это не
открывает таблицы клиентским ролям и не расходует лимиты Free в фоне.

## История

Новый контракт:

`POST /functions/v1/events`, `Authorization: Bearer <app session token>`:

```json
{
  "action": "history.list",
  "eventId": "uuid",
  "limit": 20,
  "cursor": {
    "occurredAt": "server timestamptz",
    "id": "uuid",
    "source": "expense | settlement | transfer"
  }
}
```

`cursor` необязателен, `limit` — 1–50. Ответ:

```json
{
  "items": [
    {
      "id": "uuid",
      "source": "expense | settlement | transfer",
      "action": "expense.create | settlement.settle | transfer.sent | ...",
      "actorName": "серверное имя",
      "occurredAt": "серверное время",
      "before": null,
      "after": {},
      "details": {}
    }
  ],
  "nextCursor": null
}
```

RPC `event_history_action` — `SECURITY INVOKER`; execute разрешён только
`service_role`. Пользователь определяется по хешу действующей app-сессии. Порядок
блокировок: app session `FOR SHARE` → event `FOR SHARE`; после ожидания сессия
проверяется снова, затем проверяется текущее членство. Подмена eventId, actor,
статуса, времени, before/after или details frontend-ом не принимается.

Источники — существующие неизменяемые `audit_log`, `settlement_audit_log` и
`transfer_status_history`. Сортировка стабильна по server time DESC, id DESC,
source DESC. Страница по умолчанию содержит 20 записей; кнопка дозагружает более
ранние. Идемпотентные повторы не создают новые записи истории.

  ожидаем до появления production-нагрузки.

## Реальная приёмка в Telegram

1. Открыть существующее мероприятие аккаунтами A и B; изменения A появляются у B
   после «Обновить» и после возврата Mini App на передний план.
2. Начать новый расход, отключить сеть, нажать «Сохранить» и перезапустить Mini App.
   Форма и точный pending восстановлены, успех не заявлен.
3. Повторить без изменения: объект и история создаются один раз. Затем изменить
   восстановленную форму: отправляется новый requestId.
4. Дважды быстро нажать подтверждение: выполняется один запрос.
5. Имитировать timeout/5xx: старые данные остаются, доступен явный точный повтор.
6. Истечь/отозвать сессию во время формы: повторный Telegram-вход не теряет форму
   и не отправляет мутацию автоматически.
7. Одновременно изменить расход с двух аккаунтов: устаревший экран получает
   `version_conflict`, свежие данные не перезаписываются.
8. Проверить пустые мероприятия, расходы, историю, нулевой расчёт, участника без
   действий и completed-мероприятие.
9. Проверить историю расходов, фиксации/отмены, sent/not_received/sent/confirmed и
   завершения, затем дозагрузить более раннюю страницу.
10. Убедиться, что исключённый участник и аккаунт другого мероприятия историю не
    читают.
11. Проверить 320×740 и 390×844, клавиатуру, safe area, touch, Telegram WebView и
    обычный браузер без initData; горизонтального overflow и JS errors быть не
    должно.

## Ограничения до этапа 8

- Реальная матрица iOS/Android/Desktop Telegram и длительный пилот ещё не пройдены.
- Нет фонового push/Realtime и polling; данные обновляются вручную, при возврате на
  передний план и при восстановлении сети.
- Локальные черновики не синхронизируются между устройствами.
- Нет регулярной серверной очистки журналов requestId и старых app-сессий.
- Резервная копия, восстановление и эксплуатационная проверка Supabase относятся к
  этапу 8.
- Приложение не проводит и не проверяет банковские платежи.
