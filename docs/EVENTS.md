# Этап 3: мероприятия

## Реализовано

- Создание мероприятия с названием (1–120 символов) и описанием (до 2000).
  Создатель сразу входит в число участников. Повтор создания с тем же requestId
  возвращает то же мероприятие.
- Список только своих мероприятий; карточка и имена участников доступны участникам.
- Случайная ссылка `https://t.me/raskidai_app_bot?startapp=invite_<token>`.
  Создатель создаёт, обновляет и отключает её. В БД хранится только SHA-256;
  исходная ссылка показывается после создания и хранится в памяти экрана.
- При запуске по приглашению приложение предлагает присоединиться после входа.
  start_param/tgWebAppStartParam не используются как доказательство личности.
- До 30 участников вместе с создателем; повторный вход не создаёт дубль.
- Выход участника с подтверждением; создатель не может выйти.
- Статусы draft/settled/completed: присоединение новых участников и изменения
  разрешены только в draft. Фиксация и возврат реализованы на этапе 5.
- Hash-навигация, пустое состояние, обновление списка/карточки, сообщения об
  ошибках, сохранение формы и requestId при сетевой ошибке. Автообновления пока нет.

## Серверный контракт

`POST /functions/v1/events`, `Authorization: Bearer <app session token>`, JSON:

| action  | Поля                                 | Ответ                                           |
| ------- | ------------------------------------ | ----------------------------------------------- |
| list    | —                                    | `{ events: [...] }`                             |
| create  | title, description, requestId (UUID) | `{ eventId }`                                   |
| get     | eventId                              | `{ event: { ..., members, invitationActive } }` |
| join    | invitation (64 hex-символа)          | `{ eventId }`                                   |
| rotate  | eventId                              | `{ ok: true, invitation }`                      |
| disable | eventId                              | `{ ok: true }`                                  |
| leave   | eventId                              | `{ ok: true }`                                  |

Edge Function передаёт хеш сессии в `event_action`. RPC повторно проверяет сессию
и определяет пользователя в транзакции. Ни userId, ни готовый invitationHash
от браузера не принимаются. Все новые таблицы закрыты для anon/authenticated;
RPC доступна только service_role и работает как SECURITY INVOKER.

Все операции с участниками/приглашением блокируют строку events через FOR UPDATE.
Проверка лимита и вставка участника идут в одной транзакции. После получения
блокировки приглашение и срок сессии проверяются снова. Отзыв сессии сериализуется
с выполняющейся операцией через блокировку строки app_sessions.

Ошибки: 400 — неверный ввод, 401 — сессия, 403 — права, 404 — недоступное
мероприятие/приглашение, 409 — лимит, зафиксированный статус или запрещённый выход.

## Ограничения этапа 4 — реализованы

Добавлены expenses и expense_shares с составными внешними ключами
`(event_id, author_id)` / `(event_id, user_id)` к members с ON DELETE RESTRICT.
Выход автора или получателя доли возвращает `member_has_expenses`, включая
получателя нулевой доли. SQL-тесты обоих случаев проходят. Связи не удаляются
каскадом. Все изменения расходов и долей берут ту же блокировку строки events.
Контракт расходов: [EXPENSES.md](EXPENSES.md).
Фиксация берёт ту же блокировку events и после перехода в settled блокирует
вход, выход и управление приглашением. Контракт: [SETTLEMENTS.md](SETTLEMENTS.md).

## Приёмка после публикации frontend

1. Открыть Mini App аккаунтом A и создать мероприятие.
2. Создать ссылку и открыть её аккаунтом B. Нажать «Присоединиться».
3. На обоих аккаунтах обновить карточку: видны A и B. Повторно открыть ссылку B:
   третий участник не появляется.
4. B выходит; карточка исчезает из его списка. A выйти не может.
5. A отключает ссылку; B больше не может по ней присоединиться.
6. A создаёт новую ссылку. Старая не действует, новая позволяет B войти.
7. Перезагрузить Mini App на карточке: hash-маршрут открывается без 404.
