# Этап 8: ограниченный пилот

Статус на 14.09.2026: **технически подготовлен к пилотной приёмке**.
Автоматическая часть и пользовательская приёмка фиксируются раздельно. Этап 8
не завершён: локальный restore drill и реальная матрица Telegram
iOS/Android/Desktop ещё требуют фактического выполнения.

## Границы пилота

- До 30 участников, одна валюта RUB, равные доли, суммы до
  99 999 999 999 копеек.
- Только символические отметки переводов. Приложение не выполняет и не проверяет
  банковские платежи.
- Один существующий production-проект Supabase `njzfzgqprgkyrqirkvhe` и бот
  `@raskidai_app_bot`; новые облачные проекты не создаются.
- Нет realtime/push и фонового polling. Данные обновляются кнопкой, при возврате
  на передний план и восстановлении сети.
- Черновики локальны устройству. Pending request живёт 24 часа и повторяется
  только явно с тем же requestId/body.

## Автоматическая приёмка

Обязательный набор перед каждым пилотным выпуском:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm build
deno check supabase/functions/telegram-auth/index.ts \
  supabase/functions/session/index.ts supabase/functions/events/index.ts
pnpm exec supabase start
pnpm exec supabase test db
pnpm exec supabase stop --no-backup
git diff --check
```

`supabase/tests/pilot.test.sql` использует детерминированный seed `20260914`.
Он проверяет 1 и 8 участников, 1 и 48 расходов, авторов внутри и вне состава
долей, 1 копейку, предельную сумму, остатки деления, чередование авторов,
детерминизм при другом порядке строк и все расчётные инварианты. Остальные SQL-
наборы сохраняют сценарии двух участников, CRUD до фиксации, запрет после неё,
нулевой результат, requestId replay/conflict, version conflict и переходы
переводов. Предыдущие воспроизводимые двухсоединительные race-тесты этапов 5–6
остаются доказательством неизменённого порядка блокировок; при изменении RPC или
lock order их необходимо повторить.

Арифметические инварианты:

- все денежные колонки — `bigint`, frontend принимает только safe integer;
- сумма балансов settlement равна нулю;
- общий долг, общий кредит и сумма переводов равны;
- перевод положителен, не самому себе, от должника кредитору;
- после применения переводов итог каждого участника равен нулю;
- одинаковый ввод даёт одинаковые балансы и последовательность переводов;
- порядок физического чтения строк не меняет результат;
- алгоритм ограничен `k−1` переводами, но математический минимум не обещается.

Матрица доступа SQL покрывает creator/member/removed/outsider, неизвестную,
истёкшую, отозванную и повреждённую сессию; list/get/join/invitation/leave,
expenses, settlement/cancel, transfers, history, requestId replay/conflict и
cursor. HTTP-тесты отдельно подтверждают allowlist и игнорирование `userId`,
`actorId`, status, сумм, сторон, времени и history payload. На всех 19 прикладных
таблицах проверяются RLS и отсутствие прав anon/authenticated; RPC должны быть
SECURITY INVOKER и не иметь EXECUTE для PUBLIC.

Результат подготовки 14.09.2026: 35/35 frontend/HTTP/unit-тестов, typecheck и
production build прошли; 7 облачных SQL-файлов прошли в транзакциях с rollback.
Production-read-only проверка не нашла нарушений суммы балансов, незакрытых
участников, отключённого RLS или SECURITY DEFINER прикладных RPC. В браузере
320×740 и 390×844 `scrollWidth` равен viewport, console WARN/ERROR отсутствуют.
Это автоматические доказательства, а не отметка реальной Telegram-приёмки.

## Безопасный smoke-check

После публикации всех трёх Edge Functions версии 8:

```sh
pnpm smoke -- https://njzfzgqprgkyrqirkvhe.supabase.co
pnpm exec supabase migration list --linked
pnpm exec supabase db advisors --linked
```

Smoke не содержит токенов и не меняет данные: проверяет ответы трёх функций,
отказ без авторизации, отказ для испорченного payload и заголовок
`X-Raskidai-Backend-Version: 8`. Версии миграций сравниваются с локальными
именами. Advisors проверяются отдельно, чтобы не хранить access token в CI.

## Backup procedure

Free-проект не имеет гарантированной доступной пользователю ежедневной копии;
Supabase рекомендует регулярно выполнять логический `db dump`. Используется
Supabase CLI 2.116.0 или проверенная более новая версия. Перед каждым запуском
снова прочитать `supabase db dump --help` и актуальную документацию:
[Database Backups](https://supabase.com/docs/guides/platform/backups) и
[CLI backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

Changelog проверен 14.09.2026. Для этого runbook учтены переход self-hosted
Supabase на PostgreSQL 17, исправление повторного применения актуальных
credentials после physical restore и игнорирование явного pin версии extension;
миграция поэтому не закрепляет версию `pg_cron`. Эти platform-изменения не
заменяют обязательный локальный logical restore drill.

```sh
scripts/backup.sh /path/to/encrypted-private-volume/raskidai-YYYYMMDDTHHMMSSZ
```

Скрипт отказывается писать dump внутрь репозитория, создаёт каталог с режимом
0700 и файлы 0600. Он сохраняет roles/schema/data отдельными plain-SQL файлами,
COPY-данные, контрольные количества строк, список миграций и Edge Functions,
UTC-время, CLI-версию, Git SHA, SHA-256 файлов и имена необходимых секретов без
значений. Storage objects в приложении сейчас не используются; если появятся,
их нужно копировать отдельно — database backup хранит только metadata.

Dump может содержать production-персональные данные. Его нельзя коммитить,
публиковать, оставлять незашифрованным или прикладывать к CI. После копирования
его шифруют и переносят в закрытое off-site хранилище с ограниченным доступом.

## Restore procedure и доказательство

Восстановление поверх production запрещено. Target должен быть новой одноразовой
локальной PostgreSQL/Supabase БД на `localhost`/`127.0.0.1`, желательно PostgreSQL
17 как production. Перед запуском вручную проверить пустую БД, hostname, имя БД
и версию. Скрипт дополнительно отвергает `supabase.co` и production project ref.

```sh
scripts/restore-verify.sh /secure/backup-directory \
  'postgresql://postgres:LOCAL_PASSWORD@127.0.0.1:5432/raskidai_restore_drill'
```

Проверка выполняет restore в одной транзакции с `ON_ERROR_STOP`, затем проверяет
таблицы, функции, extensions, RLS, grants, SECURITY INVOKER, ссылки, суммы долей,
балансы, направления и полное закрытие переводов, неизвестную app-сессию,
контрольные количества и весь pgTAP suite. После этого нужно отдельно запустить
Advisors локальной среды, выполнить основные read/mutation RPC на тестовых
фикстурах и удалить одноразовую БД и незашифрованную рабочую копию dump.

На текущей машине Docker, `psql` и Deno не установлены, поэтому успешное
восстановление **не заявляется**. Поле доказательства заполняется только после
drill: дата, target host/database, PostgreSQL и CLI версии, Git SHA, checksum,
совпадение counts, число pgTAP-тестов, Advisors, время восстановления и факт
удаления target/dump. Пока RPO/RTO не гарантируются. Цель пилота после первого
успешного drill: backup не реже 24 часов (целевой RPO 24 ч) и измеренный RTO,
а не обещанный заранее.

Необходимые секреты для восстановления сервиса, без значений:

- `TELEGRAM_BOT_TOKEN`;
- `ALLOWED_ORIGINS`;
- runtime-managed `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`;
- GitHub Actions variable `VITE_SUPABASE_URL`;
- Supabase access token/database password только на время backup/restore.

## Retention

Назначение `app_sessions` — серверная аутентификация; активная запись нужна до
`expires_at`. Истёкшие записи не делают токен действительным. Миграция этапа 8
добавляет SECURITY INVOKER-функцию, доступную только `postgres`, которая удаляет
не более 500 сессий, истёкших более 7 суток назад, через `FOR UPDATE SKIP LOCKED`.
Supabase Cron запускает её ежедневно в 03:17 UTC. Активные и недавно истёкшие
сессии сохраняются; лимит batch — 1–1000. Тест проверяет grants, расписание,
границу срока и batch.

`event_requests`, `expense_requests`, `settlement_requests` и
`transfer_requests` обеспечивают идемпотентность. Frontend pending TTL — 24 часа,
но поздний retry возможен после восстановления вкладки, устройства или разбора
инцидента. Удаление записи позволило бы тому же requestId повторно создать
объект/переход. Без отдельного глобального tombstone и согласованного срока
бизнес-идемпотентности безопасное удаление не доказано, поэтому request-журналы
не очищаются и cron для них не добавляется. Audit/history также сохраняются.

Актуальная реализация Cron основана на
[Supabase Cron](https://supabase.com/docs/guides/cron): `pg_cron`, SQL job,
наблюдение через `cron.job` и `cron.job_run_details`; job должен завершаться
существенно быстрее рекомендованного лимита 10 минут.

## Мониторинг и сбой

Перед пилотом и после каждого backend-релиза:

1. Проверить health проекта, versions Edge Functions и migration list.
2. Запустить smoke и Advisors security/performance.
3. Проверить последний CI: frontend tests, TypeScript/Deno, build и локальный SQL.
4. Проверить последние ошибки Edge Functions без вывода body/Authorization.
5. Проверить `cron.job_run_details` для cleanup и рост таблиц requests/history.
6. Сверить последний зашифрованный backup, checksum и дату последнего drill.

При массовых 401 сначала проверить свежесть Telegram initData и состояние
сессий; при 5xx — Edge Function logs и database health; при конфликте миграций —
остановить выпуск и сравнить migration list, не выполнять `repair` наугад. При
неизвестном результате мутации не нажимать новую операцию: использовать явный
повтор сохранённого requestId/body.

Rollback Edge Function: взять предыдущий проверенный Git SHA, проверить локально
и повторно deploy соответствующей функции. Не переносить старую функцию, если её
контракт несовместим с уже применённой схемой. Миграции откатываются только новой
forward-миграцией после backup и проверки; `db reset`, удаление/очистка production
и восстановление dump поверх production запрещены. Для retention-отката сначала
`cron.unschedule('raskidai-expired-sessions-daily')`, затем новой проверенной
миграцией удалить функцию; сами уже удалённые истёкшие сессии не восстанавливаются.

## Реальная Telegram-матрица

Ни один пункт ниже не отмечается автоматически. Для каждого клиента записать
версию Telegram/OS, аккаунт, дату и результат без Telegram ID или токенов.

- [ ] Telegram iOS, светлая тема, 390×844 или близкий viewport.
- [ ] Telegram iOS, тёмная тема, клавиатура, safe area, touch.
- [ ] Telegram Android, светлая тема, минимум 320×740.
- [ ] Telegram Android, тёмная тема, клавиатура, safe area, touch.
- [ ] Telegram Desktop, изменение размера окна и повторное открытие.
- [ ] Обычный мобильный браузер без initData показывает безопасный отказ.
- [ ] Обычный desktop-браузер без initData показывает безопасный отказ.
- [ ] На каждом Telegram-клиенте: фон/возврат, offline/online, закрытие/reopen.
- [ ] Истёкшая/отозванная сессия вызывает контролируемый повторный вход.
- [ ] Нет horizontal overflow, JavaScript errors и unhandled rejection.

Последовательность: открыть бота → создать/открыть тестовое мероприятие → пройти
обычные действия → выключить сеть на незавершённой форме → вернуть сеть → свернуть
и вернуть Mini App → закрыть и открыть снова → проверить восстановление без
автоповтора → осмотреть console там, где клиент это позволяет.

## Реальное тестовое мероприятие A/B/C

Финальная контрольная таблица (после редактирования расхода C):

| Расход          | Автор |                  Сумма | Участники |      Доля A |      Доля B |      Доля C |
| --------------- | ----- | ---------------------: | --------- | ----------: | ----------: | ----------: |
| Жильё           | A     | 60 000 коп. (600,00 ₽) | A/B/C     |      20 000 |      20 000 |      20 000 |
| Билеты          | B     | 30 000 коп. (300,00 ₽) | A/B       |      15 000 |      15 000 |           0 |
| Такси           | C     | 12 000 коп. (120,00 ₽) | B/C       |           0 |       6 000 |       6 000 |
| **Итого paid**  |       |                102 000 |           |      60 000 |      30 000 |      12 000 |
| **Итого share** |       |                102 000 |           |      35 000 |      41 000 |      26 000 |
| **Баланс**      |       |                      0 |           | **+25 000** | **−11 000** | **−14 000** |

Ожидаемые переводы: B → A 11 000 коп. (110,00 ₽), C → A 14 000 коп.
(140,00 ₽). Это только отметки в приложении, реальный банковский перевод не нужен.

1. A создаёт мероприятие, приглашает B/C; все сверяют участников.
2. Добавить три расхода. C сначала вводит 100,00 ₽, затем меняет на 120,00 ₽.
3. С двух устройств открыть один расход; сохранить на одном, на втором получить
   `version_conflict` и убедиться, что свежие данные не перезаписаны.
4. Создать временный расход-маркер, выполнить не менее 20 create/update/delete
   записей истории и удалить его до фиксации — это обеспечивает реальную
   проверку второй cursor-страницы без влияния на итог.
5. Во время новой формы отключить сеть/reload; проверить черновик и pending,
   затем выполнить явный точный retry один раз.
6. A фиксирует settlement. Все три аккаунта вручную сверяют таблицу выше.
7. B отмечает sent, A — not_received, B снова sent, A — confirmed.
8. C отмечает sent, A — confirmed. Проверить автоматический completed.
9. Проверить полную историю и дозагрузку без дублей, затем запреты расходов,
   входа/выхода, приглашения, cancel и переходов confirmed.
10. Повторно открыть Mini App на iOS/Android/Desktop и сверить один результат.

Дата, аккаунты A/B/C, клиенты и фактические результаты пока не заполнены;
мероприятие не считается проведённым заранее.

## Известные ограничения после подготовки этапа 8

- Restore drill и измеренный RTO отсутствуют до появления Docker/PostgreSQL 17.
- Реальная Telegram-матрица и мероприятие A/B/C требуют физических устройств.
- Нет гарантированного RPO на Free; требуется внешний зашифрованный backup.
- Request/history retention не ограничен; рост нужно наблюдать в пилоте.
- Нет автоматического мониторинга и алертов; используется ручной предрелизный
  checklist.
- GitHub Pages публикуется только отдельным ручным workflow и не входит в эту
  автоматическую подготовку.
