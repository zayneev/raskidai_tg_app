## Поведение

- Создание, список, редактирование и удаление расходов в карточке мероприятия.
- Плательщик всегда автор из серверной сессии, при редактировании не меняется.
- Только RUB: отдельное поле валюты не принимается. Ввод рублей с запятой или
  точкой, не более двух десятичных знаков; без округления лишних знаков.
  Хранение — bigint копейки, от 1 до 99 999 999 999 (999 999 999,99 ₽).
  Ограничение сохраняет точность при передаче чисел в JavaScript.
- Выбор от 1 до 30 участников; можно исключить себя. Дубли ID и участники
  другого мероприятия отклоняются.
- Доли = целая часть суммы / число выбранных; оставшиеся копейки получают
  первые UUID в возрастающем порядке. Нулевая доля допустима при малой сумме.
- Участник изменяет/удаляет свои расходы, создатель — любые. Все участники
  видят расходы и историю, включая снимки до/после, исполнителя и время.
- История сохраняется после удаления расхода. Записи содержат имена на момент
  изменения; серверная роль может только читать и добавлять их.
- Изменения доступны только в draft. Чтение доступно и после фиксации.

## Контракт

`POST /functions/v1/events`, `Authorization: Bearer <app session token>`, JSON.
Все действия ниже включают `eventId` (UUID).

| action           | Дополнительные поля                                            | Ответ                     |
| ---------------- | -------------------------------------------------------------- | ------------------------- |
| expenses.list    | —                                                              | `{ expenses: [...] }`     |
| expenses.history | —                                                              | `{ history: [...] }`      |
| expenses.create  | requestId, title, amountKopecks, memberIds                     | `{ ok: true, expenseId }` |
| expenses.update  | requestId, expenseId, version, title, amountKopecks, memberIds | `{ ok: true, expenseId }` |
| expenses.delete  | requestId, expenseId, version                                  | `{ ok: true, expenseId }` |

`requestId` и `expenseId` — UUID. `version` — версия из списка расходов.
Ответы расходов используют `author_id`, `author_name`, `amount_kopecks`,
`version`, `shares: [{ user_id, display_name, amount_kopecks }]`.
История: `actor_name`, `action`, `created_at`, `before_data`, `after_data`.

Ошибки: 400 invalid_input/invalid_action; 401 unauthorized; 403 forbidden;
404 not_found; 409 event_locked/version_conflict/request_conflict.
Выход участника через прежнее действие leave возвращает 409 member_has_expenses.

## Транзакции и повторные запросы

Edge Function передаёт только разрешённые поля и SHA-256 токена в
`expense_action`. RPC самостоятельно определяет пользователя, проверяет
сессию и членство; затем права автора/создателя, статус и версию.
Порядок блокировок совпадает с event_action: app_sessions FOR SHARE →
events FOR UPDATE → изменение расхода/долей. После ожидания блокировки
проверяется срок сессии снова. Отзыв сессии сериализуется через app_sessions.
Фиксация этапа 5 берёт ту же блокировку events; конкурентная проверка описана в
[SETTLEMENTS.md](SETTLEMENTS.md).

Составные FK автора и получателя доли к members используют ON DELETE RESTRICT.
Доли также ссылаются на `(event_id, id)` расхода, исключая связь с другим
мероприятием. Каскадного удаления связей с участниками нет. Deferred constraint
triggers проверяют непустой набор долей и равенство их суммы расходу.
При удалении RPC явно удаляет доли, затем расход; аудит остаётся. После удаления
всех актуальных связей участник может выйти. Само наличие записи в истории
выход не блокирует; автор исключённый из долей и получатель нулевой доли — блокируют.

expense_requests хранит уникальную тройку event/actor/requestId, точное тело
запроса и успешный ответ в одной транзакции с расходом и аудитом. Повтор возвращает
исходный ответ даже после удаления расхода, не создаёт повторную запись истории
и не увеличивает версию. Другое тело с тем же ключом — request_conflict.
Повтор всё равно требует действующую сессию и членство. Проверка версии защищает
от потери параллельного изменения (409 version_conflict).

При неоднозначной сетевой ошибке форма и точное тело с requestId остаются
в памяти экрана; до ответа доступен повтор отправки. При определённой ошибке
4xx форму можно исправить/закрыть; при конфликте версии нужно обновить список
и открыть расход заново. Перезагрузка или уход с экрана сбрасывают форму — после
этого сначала проверьте список. Между устройствами формы не синхронизируются.

Все таблицы закрыты для anon/authenticated, RLS включён без разрешающих политик.
RPC и вспомогательные функции — SECURITY INVOKER, доступны только service_role.
Привилегированных ключей во frontend нет.

## Приёмка после публикации frontend этапа 4

1. A создаёт мероприятие; B присоединяется по приглашению.
2. B создаёт расход 100,01 ₽ на A и B; сумма долей — 10001 копейка.
3. B исключает себя: плательщик остаётся B, вся доля у A. B выйти не может.
4. A изменяет расход B; B не может изменить расход A.
5. Оба видят историю до/после с именем исполнителя. Устаревшая версия не
   перезаписывает новое изменение.
6. Повторить запрос после обрыва сети: один расход и одна запись истории.
7. Удалить расход с подтверждением: он исчезает из списка, остаётся в истории.
8. B выходит только после удаления всех его связей с актуальными расходами.

Публикация frontend — прежний ручной workflow Pages из README. Секреты,
проект Supabase и настройки бота менять не требуется.
