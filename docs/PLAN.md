# План MVP «Раскидай»

## Решения

- Telegram Mini App, до 30 участников на мероприятие, включая создателя.
- Только рубли, хранение в целых копейках, равное деление.
- Плательщик — автор расхода. Можно исключить себя из разделения.
- Участник изменяет свои расходы, создатель — любые. Изменения видны в истории.
- Все участники видят все расходы и переводы.
- Вход по отключаемой/обновляемой случайной ссылке до фиксации расчёта.
- Выход допустим только при отсутствии связей с расходами. Создатель не выходит.
- «Раскидать» фиксирует расчёт и блокирует расходы и присоединение.
- Возврат к редактированию — только до первой отметки отправки перевода.
- Отправитель отмечает отправку, получатель подтверждает или сообщает «Не получил».
- Приложение не проводит и не проверяет банковские платежи.
- После всех подтверждений мероприятие завершено. При нулевых балансах — сразу.

## Архитектура

React + TypeScript + Vite → Supabase Edge Functions (TypeScript/Deno) → PostgreSQL.
Frontend размещается на GitHub Pages, backend и БД — Supabase Free.
Отдельный Node.js-сервер не нужен. Node.js используется для frontend tooling.

Сервер проверяет подпись и свежесть Telegram initData, затем выдаёт сессию.
Нельзя доверять пользовательскому ID из браузера. Права проверяются сервером.
Модель доступа к БД на этапе 2: запрет прямого доступа anon/authenticated к
прикладным таблицам; все операции через авторизованные Edge Functions.
Транзакционные операции выполняются PostgreSQL-функциями, вызываемыми сервером;
не серией независимых HTTP-запросов. Привилегированные ключи — только на сервере.

Free: учитывать лимиты базы/функций и паузу при низкой активности. GitHub Pages
используется для некоммерческого пилота из публичного репозитория.

## Сущности будущей схемы

Users: ID, уникальный Telegram ID, отображаемое имя.
Events: ID, создатель, название/описание, статус, версия.
Members: уникальная пара event/user, время входа.
Invitations: хеш случайного токена, мероприятие, активность.
Expenses: мероприятие, автор, название, сумма копеек, версия, время.
ExpenseShares: расход, участник, доля в копейках.
Settlements: мероприятие, версия/снимок, активен/отменён, время.
Transfers: расчёт, отправитель, получатель, копейки, статус и времена.
AuditLog: автор, действие, объект, изменения, время.

Ограничения: положительный расход; минимум один получатель доли; получатели
состоят в мероприятии; сумма долей равна расходу; лимит участников атомарен.

## Расчёт

Деление целочисленное; оставшиеся копейки распределяются по стабильному порядку
ID участников. Доли сохраняются с расходом. Баланс = оплачено − доли.
Сумма балансов равна нулю. Сопоставляем наибольший долг с наибольшим кредитом,
переводим минимум двух остатков, повторяем. При равенстве выбираем по ID.
Не более k−1 переводов для k ненулевых балансов; абсолютный минимум не гарантирован.
Приоритет — правильный баланс и небольшое общее число переводов.

Пример: Аня платит 6000 за А/Б/В/Г, Борис 3000 за А/Б/В, Вера 800 за В/Г.
Балансы: А +3500, Б +500, В −2100, Г −1900 рублей.
Переводы: В→А 2100, Г→А 1400, Г→Б 500.

## Этапы и критерии

1. **Основа.** Каркас, стартовый экран, конфигурация Supabase, документация,
   CI и workflow Pages. Готово, когда типы и production build проходят,
   экран открывается под `/raskidai_tg_app/`. Публикация проверяется отдельно.
2. **Telegram-вход.** Настройка бота, проверка initData, сессия, users и защита
   доступа. Реальный вход работает; поддельные/просроченные данные отклоняются.
3. **Мероприятия.** Создание, список, приглашения, участники и выход. Два аккаунта
   попадают в одно мероприятие; 31-й участник и отключённая ссылка отклоняются.
4. **Расходы.** Формы, доли, права, история изменений. Корректное округление;
   повторная отправка не создаёт дубль, участник не меняет чужой расход.
5. **Расчёты.** Балансы, фиксация, снимок, переводы. Эталонный пример проходит;
   конкурентная запись расхода не нарушает зафиксированный результат.
6. **Переводы.** Отправка, подтверждение, проблема, завершение и разрешённый
   возврат к редактированию. Нельзя пересчитать после первой отметки отправки.
7. **Устойчивость.** Обработка сети, конфликтов и повторов, история и пустые
   состояния, сохранение формы при ошибке. Права реализуются с этапов 2–4.
8. **Пилот.** Тесты арифметики и доступа, iOS/Android/Desktop Telegram, резервная
   копия и проверка восстановления; реальное тестовое мероприятие.

После этапа 5 доступен сквозной сценарий до списка переводов.
Каждый этап завершается отдельным проверяемым изменением.

## Статус этапа 2

Реализованы код входа, сессия с отзывом и сроком 24 часа, users, миграция
с закрытым доступом клиентских ролей, тесты подписи и HTTP-обработчиков,
SQL-тесты доступа и жизненного цикла сессии. Инструкция подключения:
[TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

Остаётся применить миграцию и функции на стенде, настроить бота и проверить
реальный вход. До этой приёмки этап 2 не отмечаем выполненным.

## Проверки будущих этапов

Копеечные остатки, исключение плательщика, только один получатель, нулевые
балансы, отсутствие расходов, полное закрытие балансов переводами.
Подмена ID и доступа, повторные запросы, гонка расход/фиксация, гонка входов,
устаревшие версии, отключённые ссылки и изменение отменённого расчёта.

## Не входит

Проведение платежей, несколько валют, неравные доли, чеки, передача роли
создателя, исправления после начала переводов, математически точный минимум.
